## Purpose & typical use
Every boot of the dev server logged a handful of `Couldn't remap old Modification Id … AbilityGroupSlotModificationBuffer`
errors. They come from slot-override **holders**. When the game applies a slot-override row, the engine creates a
prefab-less entity (`ReplaceAbilityOnSlotBuff_AllInitialized` + `AbilityGroupSlotModificationBuffer`) that is the
source of three mods per slot: GroupGuid (which ability), CopyCooldown and SpellModsSource. Beelzebub's bar reset and
grant pop the GroupGuid mod by id. The holder keeps its other two mods, so the engine never destroys it. It is saved,
and at the next boot its dead ids fail to remap or, worse, get remapped onto other mods' ids. The diagnostic on
2026-10-04 also found a gameplay effect: six stale holders forced slot 7's `CopyCooldown` to False (base True). This
slice cleans such holders: the heartbeat finds a holder none of whose rows still sets a slot, confirms it on a
second read, clears its leftover mods through the engine and destroys it. Users are the server owner (clean boots)
and players (correct cooldown sharing); nobody runs anything new.

## Use cases
### Typical
- The owner boots the server: the first boot after the update logs `[Beelz MODLEAK] sweep (boot): cleaned 7 …`; the next boots have no remap error (D10, D12).
- A player runs `.beelz resetbar CONFIRM`: a couple of seconds later the sweep cleans the holders the reset left (D5, D11).
- An admin checks one player with `.beelz admin modleak Chaos`: the reply counts holders by verdict; details go to the log (D6, D11).
### Minimal stretch
- A server with no stale holder: the boot sweep reads, finds nothing, logs `sweep (boot): nothing stale among <n> player holder(s)` and sleeps; a pop-armed pass that finds nothing logs the same idle line only with `VerboseLogging` on (D4, D5, A1).
- A player whose holders are all live: nothing is touched (D2).
### Maximal stretch
- A slot dump mid-change (the engine still applying a new row): a holder read stale once is kept, re-read 2 s later, and cleaned only if still stale (D3). The confirming read and the clean run in the same `Tick` call on the main thread, so no pop or apply lands between them; a row applied later belongs to a new holder entity (new index/version), which the confirm never matches (D3).
- A holder still being built (no `AllInitialized`) or a slot whose dump does not parse: never cleaned (D2).
- Volume (100×): 40 players × 25 holders = 1 000 holders; one pass reads each holder's buffer and parses each target slot once (cached per slot). A pass reads at most 4 096 holders, in ascending entity index from a cursor; beyond that the line says `the rest not read`, the cursor moves past the last holder read and the sweep re-arms, so the next pass reads the following page — every holder is reached within ceil(n / 4 096) passes even when all earlier ones stay live (D22). Passes only run after a boot or a pop, never every frame.
- Used once (8.2): nothing is persisted by this slice; the sweep state is three static fields reset by every pass.
- Abuse: players cannot reach the sweep or the report; the sweep runs on its own and the report is admin-only (D6).

## Business rules
1. A row is **Live** only when its GroupGuid id is among the target slot's GroupGuid mods **with this holder as source** (D1). Id alone is not enough: the boot remap already put dead ids onto other mods' ids (holder 327222 row → 1540, 327223's CopyCooldown mod).
2. A holder is **Stale** only when it is initialized, every slot it targets was read, and none of its rows is Live (D2). One live row keeps the whole holder.
3. Only holders stale in two reads at least 2 s apart are cleaned (D3). Pops coalesce (on a monotonic clock, so a wall-clock jump cannot shorten the 2 s gap — A4): the first `MarkDue` arms the pass and later ones neither postpone nor restart it (`ModLeak.Arm`, D3), so command spam cannot starve the sweep; a holder a later pop makes stale is seen once by this pass and confirmed by the next.
4. Cleaning order: `ClearLooseSourceModifications(holder)` first (removes its CopyCooldown and SpellModsSource mods so the slot falls back to its base), mark the target slots dirty, then `DestroyUtility.Destroy` (D5).
5. "Every pop" (4.5) is computed by searching the plugin for `RemoveAbilityGroupModificationOnSlot` at `681f313`: two call sites, `SlotApply.PushOnSlot` and `TransformBuffService.PopSlotModifications` (inside the local function `Pop`). The `wiring` check repeats that search over every `.cs` file on every run, so a third pop site that does not mark FAILs. Blind spot: a pop through another engine API (`ModificationsRegistry.RemoveModification` directly) — none exists today; `/code-review` and Codex read the diff for one.
6. Conflict order: safety first (never clean what is not proven stale: D1–D3), then cleanup (clean every confirmed holder), then the log budget. Only the project owner may approve an exception (e.g. a manual one-off cleanup or a per-server switch), and only through a plan amendment.
7. Holders that target non-players are left alone (the scan accepts a holder only when every row targets a `PlayerCharacter`): NPC and boss holders are vanilla's own.

### States
- Sweep states: idle (`_dueAt` = MaxValue); due (first read at `_dueAt`); first read held (second read ≥ 2 s later); after the second read it cleans and goes idle, or re-arms when a holder was seen stale only once or the pass was capped (D3, D5).
- Concurrency (7.2): every caller (`Pulse`, commands, `TryInitialize`, the pops) runs on the server main thread; the race is across frames — the engine applying a new row in frame N while the sweep reads in frame N+1 — covered by the two-read confirm and the `AllInitialized` gate (D2, D3).
- Interrupted (7.3): a server stop between the reads loses only the in-memory first read; the next boot marks the sweep again (D5). A clean that throws keeps the holder and logs a warning; the next pass retries it.
- Empty/first-run (7.1): no holders → the first read finds nothing and the sweep sleeps without a line (D5).
### Permissions
- Actors (2.1): (a) decided: an ordinary player MAY arm the sweep, through their own self-only `grant`/`resetbar`/`clearbar` (the pops), and that is all they can do — arming only schedules a pass 2 s later; the pass itself cleans only holders that `ModLeak.Select` proves stale, on every player's character, which is maintenance with no player-chosen target, and passes coalesce (`ModLeak.Arm` keeps one due time) so spamming a command costs at most one pass per 2 s and never postpones it (D3); (b) admins reach the read-only `modleak` report (adminOnly); (c) server console/RCON run no VCF command. D6 checks (b), that only `Tick` calls `Clean`, that only the three pop/boot methods arm the sweep, and — through `check_clearbar.py actors` — that the commands reaching the pops keep their self-only / adminOnly reach.
- Unauthorised path (2.2): VCF's standard deny for adminOnly; the report changes nothing.
- Ownership (2.3): a holder belongs to the player character entity its rows target (identity = entity index + version). An offline character still exists in the world, so its holders are swept like an online one's. A deleted character's holders target a dead entity, fail the `PlayerCharacter` filter and are never touched (vanilla's to clean up); if vanilla leaves them, their dead ids keep logging the remap error — a residual this slice accepts and does not hide: `.beelz admin modleak all` does not list them (no player target), and the README caveat names the case. A recycled entity index carries a new version and is another entity. Characters are not transferred between accounts in V Rising. The sweep never takes a player from input; the report takes one only to read.
### UX
- Discovery (11.1): admins find `modleak` through VCF's generated `.help` listing for `.beelz admin` and the README admin cheat-sheet (one line added in the release commit, D16).
- No player-facing change except that cooldown sharing on slot 7 is correct again (D11).
- Input (3.1): `.beelz admin modleak` (omitted → the caller), `.beelz admin modleak all` (case-insensitive), or `.beelz admin modleak <name>` resolved by the existing `TryBarTarget` (same rules as `bar`/`bar-raw`: no or several matches → `No (or ambiguous) player match for '<name>'.`, offline players resolve like online ones). VCF splits on spaces and passes one token; the name is echoed through `BarResetReply.Name` (log-safe, `<`/`>` dropped) and every reply through `BarResetReply.Cap`, so an over-long or odd name cannot break the line.
- Admin: `.beelz admin modleak [player|all]` replies one line `modleak <who>: <n> slot-override holder(s), <m> row(s) — live a, stale b, unreadable c, building d, empty e. Details: LogOutput.log [Beelz MODLEAK].` (under the chat cap via `BarResetReply.Cap`).
- Accessibility (11.3): the report is one plain chat line in V Rising's own chat box, which supplies keyboard entry, font and contrast; screen readers are not supported by the game client, so none apply to a chat-only command. Long lines wrap in the chat box; `BarResetReply.Cap` keeps the line under the 480-byte chat cap, and the details live in the log.
- Activation (11.4): the sweep runs on its own after boot and after every pop; the `[Beelz MODLEAK] sweep` line shows it acted (D10, D11).

Personal data: SteamIDs already on every `[Beelz]` line; MODLEAK lines add entity ids and mod ids only. Logs stay on the owner's machine.

## Performance
- Throughput (13.1): a pass reads every holder buffer once and parses each target slot once (cached); passes run only after boot or a pop, at most one read per 2 s while due. Budget (S-4): the confirming pass (second read + cleaning) takes at most 250 ms at the dev server's boot (the largest batch it will see: the saved pile-up), measured by the `ms` on the sweep line and recorded by D10's `bootsweep` check, which names an overrun without failing (S-4). A pass is a one-off hitch after a boot or a pop, not per frame.
- Bounds (13.2): a pass reads at most `ModLeak.Cap` = 4 096 holders (a page; D22 pages past it). Source: 40 players × 6–8 slots × up to ~10 holders each in the worst diagnostic pile-up = ~3 200; 4 096 is the next power of two. At the bound the pass stops, says so on the sweep line, moves its cursor and re-arms; the next pass reads the next page (D4, D22).
