# Editing the shipped ability data (dev workflow)

Two hand-editable JSON files hold everything the mod ships about abilities. **Edit them directly
in the repo, rebuild, and the new data is baked into the DLL** — no in-game commands needed.
Both live in `Beelzebub/Beelzebub/Resources/` and are embedded resources (`<EmbeddedResource>` in
`Beelzebub.csproj`).

| File | Holds | Keyed by |
|---|---|---|
| **`ability_metadata.json`** | **Descriptive** — `name`, `description`, `school`, `type`, `categories`, `icon`, `sourceNpcs`, `parameters`, `incompatible`/`incompatibleReason`, `condition`/`conditionDescriptor`/`conditionModifiers`/`conditionSource`, `sourceLevel`/`sourceTier`/`isVBlood` (generated by `tools/merge_tier_into_metadata.py`). | ability-group **GUID** (string) |
| **`ability_rules.default.json`** | **Policy / config** — per-ability `Enabled`, `Weapons`, `Forms` (whitelist or `!`blacklist), `TransformOnly`, `AllowDenied`, `Difficulty`, `Phase`, `Category`, `ReviewStatus`, all shaping (`CooldownSeconds`, `MaxRangeOverride`, `AoeRadius`, `ProjectileSpeed`, `EffectDurationSeconds`, `HealingMultiplier`, `ForceTimeoutSeconds`, summon governance, interrupt/free-move/cast-speed), `Notes`; plus the global `DenyPatterns`/`AllowPatterns`/`DenyGuids`/`AllowGuids`. | ability prefab **NAME** (e.g. `AB_Nun_AoE_AbilityGroup`) inside `AbilityMap` |

## How shipping works
- On **rebuild**, both files are embedded into `Beelzebub.dll`.
- `ability_metadata.json` is read at startup as the descriptive baseline (admin server-side
  `ability_metadata_overrides.json` can override per-server).
- `ability_rules.default.json` is **seeded onto a fresh server** the first time it runs (when no
  `BepInEx/config/kdpen.Beelzebub/ability_rules.json` exists yet). Existing servers keep their own
  `ability_rules.json` — the seed never overwrites a live config. Admins can still change anything
  afterward with `.beelz admin` commands.

## Editing `ability_rules.default.json` (the config you'll tune from tester feedback)
Add/edit entries under `AbilityMap`, keyed by the ability's prefab name. Only include the fields you
want to set — everything else uses defaults. Examples:

```jsonc
"AbilityMap": {
  "AB_Militia_Fabian_Mountup_AbilityGroup": { "Enabled": false, "Notes": "server-crash — disabled" },
  "AB_Some_Sword_Combo_AbilityGroup":       { "Weapons": ["Sword", "GreatSword"] },     // whitelist: sword/greatsword only
  "AB_Some_Boss_Spell_AbilityGroup":        { "Forms": ["!Mounted"] },                  // blacklist: every form EXCEPT mounted
  "AB_Some_Heal_AbilityGroup":              { "HealingMultiplier": 0.5, "CooldownSeconds": 30 }
}
```
- **Weapons** (valid): `Sword, GreatSword, Axe, Mace, Spear, Daggers, Crossbow, Longbow, Pistols, Reaper, Whip, Claws, Pollaxe, Slashers, TwinBlades, FishingPole, Unarmed, Magic`. A bare list = WHITELIST (usable only there); a `"!X"` token = BLACKLIST (usable everywhere except X). Empty = universal.
- **Forms** (valid): `Wolf, Bear, Rat, Spider, Toad, Werewolf, Gargoyle, Mounted`. Same whitelist / `!`blacklist rule.
- **ReviewStatus** (valid): `Unreviewed, Reviewed, Approved, Blocked, Hidden`. Default `Unreviewed`. In-game: `.beelz admin ability <id> reviewstatus <val>`. **Curation lever (v0.115.0):** with `Curation_EnforceReviewStatus` ON (default), **`Blocked`** (incompatible/unwanted) and **`Hidden`** (junk) are a HARD GATE — those abilities are not capturable/grantable and are dropped from the player catalog + collection total (enforced even in `Capture_InclusiveMode`). `Unreviewed`/`Reviewed`/`Approved` are always collectible. So: curate → `Approved`; block a bad one → `Blocked`/`Hidden`. (`Enabled=false` remains the separate per-ability kill-switch; either one blocks.)
- **ReviewTag** (canonical, free-text allowed): `emote, feed, idle_flee, variant_hard, basic_attack, reaction, combo, summon, lifecycle, dev`. The audit-assigned TYPE for grouped follow-up/testing; paired with `ReviewStatus=Reviewed` it's the test-log backlog (`docs/ABILITY_TEST_LOG.md`). NOT a runtime gate. In-game: `.beelz admin ability <id> reviewtag <val>`. Emitted on the API (`review_tag=`, ApiVersion ≥ 25) so a group can be pulled in-game.
- Keys are **PascalCase** (matches the serializer). Note: cooldown/cast-time *display* values are read live from the game prefab — only the `*Override`/shaping fields here change behavior.

## Editing `ability_metadata.json` (descriptive)
Edit fields in place by GUID. Safe to hand-edit for descriptions / categories / `condition` / `incompatible`.
⚠ It's partly **generated** by `tools/` (scrape → process → merge → conditions). If you re-run that
pipeline it can overwrite freehand edits — so either edit directly and don't re-run the scrape, or put
long-lived descriptive curation in the server's `ability_metadata_overrides.json`. The condition-merge
step (`tools/merge_conditions_into_metadata.py`) preserves any entry whose `conditionSource` is
`confirmed`/`admin`.

## The loop
1. Get tester feedback (e.g. "ability X should be mounted-locked / disabled / its condition is Y").
2. Edit `ability_rules.default.json` (policy) and/or `ability_metadata.json` (descriptive).
3. `dotnet build` → data is embedded. Package as usual (`dist/` is auto-staged).
4. Fresh servers ship with your curation; existing servers can adopt it by deleting their
   `ability_rules.json` (it re-seeds) or via `.beelz admin reload` after replacing it.

## Staying in sync (there's only one source of truth)

A common worry: "is the copy in the DLL the same as the file I'm editing?" **Yes — they're the same
file.** `Resources/ability_metadata.json` and `Resources/ability_rules.default.json` are embedded into
the DLL **at build time**. There is no second "integrated" copy to maintain — editing the Resources
file and rebuilding makes the shipped data identical to what you edited. A change is made in **one**
place.

The two divergences to actually watch (the `ability-data-sync-reminder` hook + CLAUDE.md cover these):
1. **Stale embed** — you edited the source but didn't rebuild/redeploy. The fix is just: rebuild.
2. **Runtime-only change** — a `.beelz admin` command edits a *live server's* `ability_rules.json`,
   which never flows back to the shipped default. A decision meant for the package must be written into
   `ability_rules.default.json` here.
3. **Conflict** — if a change would overwrite an existing shipped `Enabled`/`Weapons`/`Forms`/`condition`
   value, confirm the overwrite is intended before doing it.

When Claude changes ability data on your behalf, it makes the change in the Resources source file (the
one editable-and-shipped copy) and rebuilds — never leaving a curation change applied only at runtime.

## Reviewing the whole set
- **`python tools/export_review_csv.py`** → `tools/ability_review.csv` — read-only join of BOTH files by
  GUID into one spreadsheet (16 columns: descriptive + policy + a computed `usability` rollup
  `Working/Conditional/Broken/Combo/Junk` and the `reviewStatus` column). The bulk-review surface; edits
  still happen in the JSON, then re-run to refresh.
- **`python tools/lint_ability_data.py`** — validate before packaging. ERRORs (orphan rule, invalid
  weapon/form/status/category/difficulty token, bad phase, duplicate key) exit non-zero to gate preflight;
  WARNINGs (a metadata-`incompatible` ability still `Enabled`, a dangling condition) are advisory. Run it
  after any hand-edit here.
- Also `tools/classify_conditions.py` (→ unit-grouped `ABILITY_CONDITIONS_AUDIT.md`) for the condition view.
